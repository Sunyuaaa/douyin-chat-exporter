> 本文是代码审查 + 本机 `exports/`、`boot.log` 实测得出的问题清单。
> 撰写时间：2026-10-11（第一轮，当时只改界面 7 项）；
> 第二轮（同日）已把下列各项按「处理」小节逐条修掉，剩下的是需要真实账号才能确认的边界。
> 每条给出：现象、证据、影响、处理、优先级、剩余边界。

## 1. CSV 导出实际落盘 0 字节，UI 却报「导出完成」 · P0 → 已修

**现象**：勾选 JSON/HTML/TXT/CSV 导出后，`exports/Sxxxx/Sxxxx.csv` 是 0 字节文件，界面显示
`✓ CSV 导出完成`，用户以为已经拿到表格。

**证据**（`boot.log` 最后一次导出，共 421 行、11 次导出完成记录）：

```
20:20:08.958 [导出] Sxxxx.txt（218202 字节）      ← Python 侧有落盘日志
20:20:08.962 [JS] [v1.1] 导出完成: txt × 1 会话
20:20:08.997 [JS] [v1.1] 导出完成: csv × 1 会话   ← 只有 JS 侧成功，没有 [导出] 行
```

磁盘 `Sxxxx.csv` 的 mtime 正好是 `20:20:08.991`，大小 0。已用当前 venv 验证：
`Path.write_text('', encoding='utf-8-sig')` 至少写 3 字节 BOM，
所以这个 0 字节文件**不是 `finish_export` 正常写完的产物**，形状是「文件被打开截断后写入抛异常」。

**定位到的假成功判定（确凿 bug）**：`deliver()` 的一次性写入兜底用
`String(ret).indexOf('失败') === 0` 判断成败，而 Python 返回的是 `'保存失败：…'`——
前缀对不上，**失败被当成成功**上报给用户。这与观察到的「UI 报完成、磁盘没内容」完全吻合。

**处理**（`test_export.py` 30 条断言 + harness 三种失败注入已验证）：
1. `save_export` / `finish_export` 改为返回结构化 `{ok, name, size, error}`，JS 只看
   `ok === true && size > 0`，彻底不猜文案；
2. 落盘改为 `write_text_atomic`：先写 `.part` 再 `os.replace`，**异常时不会再留下 0 字节文件**；
   同时 `newline=""` 修掉 CSV 的 `\r\n` 被翻译成 `\r\r\n`；
3. `clean_text` 剔除孤立代理项（JS 里 `slice(0,60)` 切断 emoji 代理对是现实来源），
   写 UTF-8 不再抛 `UnicodeEncodeError`；
4. 空内容 / 非法 eid / 落盘为 0 都在 Python 侧就判失败并写日志，分块中途失败会调 `cancel_export` 收句柄；
5. 失败链全程留痕：`分块落盘失败 → 改一次性写入重试 → 导出落盘最终失败 → 导出失败明细`；
   `doExport` 返回失败数，弹窗与底部文案改为「导出结束：N 项失败」并弹红色 ✗ 提示，**不再假报成功**；
6. JS 侧不再自己加 BOM（由 Python 的 `utf-8-sig` 负责），消除双 BOM。

**剩余边界**：那一条具体是哪个字符触发写入异常，只能在真账号复现时由新日志确认；
但无论触发点是什么，现在的行为是「写不出就明确报错」，不会再静默产出空文件。

## 3. 本目录没有成品 exe，README 与实物不一致 · ~~P2~~ 已修（1.1 收尾时打包完成）

**现象**：`README.md` 写「双击 `DouyinExporter.exe`」，但本目录只有源码，没有 exe，
也没有 `_build/`、`dist/`；接手者照 README 双击会失败。

**处理（当时）**：用户明确那一轮不打包，所以改为让文档说实话——README 顶部目录树标注「源码交接版，
未附 exe」，「直接使用」小节加了醒目提示：无 exe 时双击 `启动.bat`；并补了自行打包的命令。
`tools/precheck_release.py` 会在没有 exe 却声称有成品时给出警告，以后不一致会被自动抓到。

**处理（1.1 收尾）**：用户要求打包收尾，已用 `DouyinExporter.spec` 打出单文件
`DouyinExporter.exe`（约 29MB），并真机跑过一次：`injector.js` 从 `_MEIPASS` 读到、
`im-schema.json` 读程序目录那份（便于外部改）、`[标题栏] … hr 全 0`、`图标=True`、
登录态沿用（98 个会话）。文档随之改回「已随附成品」。
两个打包决定记在这里：
- **`imageio-ffmpeg` 被 spec 排除**：它自带 87MB ffmpeg 二进制，contrib 的 hook 会整份收进来，
  onefile 会翻倍且每次启动都要解压。改为「系统 PATH → 程序目录里的 `ffmpeg.exe` → pip 版」三档查找
  （`app.ffmpeg_exe()`），exe 用户装系统 ffmpeg 或把 `ffmpeg.exe` 丢在 exe 旁边即可。
- **`tools/gen_icon.py` 产的旧 `app.ico` 已删**：图标换成 `make_icon.py` 那套简笔画，
  spec 的 `icon=` 与 `datas` 都指向 `app-icon.ico` / `app-icon-dark.ico`。

**遗留**：无（分发前仍需删 `Data/`、`exports/`、`boot.log`，见第 4 节与 precheck）。

## 4. 隐私与密钥：Data/ 与 llm_config.json 是明文的 · ~~P1~~ 已修

**现状**：
- `Data/EBWebView/` 是完整登录态（Cookie），拿到即可直接进入账号；
- `Data/llm_config.json` 曾以**明文**保存 ASR 的 `api_key`；
- `exports/` 是真实聊天内容与媒体（本机现存 4 个会话，其中一个为空目录）；
- 远程调试口 9222 默认关闭、需 `DY_DEBUG=1` 才开，这一点本来就做对了。

**处理**：
1. API Key 改为 Windows **DPAPI**（`CryptProtectData`，当前用户绑定，ctypes 直接调、不加依赖）
   存成 `api_key_dpapi`；旧明文在首次读取时自动迁移；DPAPI 不可用时退回明文并写日志（不静默失败）。
2. **明文 Key 不再回传给页面**：`get_llm_config` 只回 `has_key / key_protected / api_key_mask`，
   输入框永远留空、占位符显示掩码——注入脚本跑在抖音页面里，少一份机密就少一份风险。
   保存时留空＝沿用已存的 Key，另设「清除 Key」按钮（`clear_key=True`）。
3. 齿轮新增「清除登录态」：写 `BASE/.logout_pending` 标记，下次启动在建窗（WebView2 锁 Data/）之前
   删除整个 `Data/`；删不干净（被占用）就保留标记下次再试。按钮要连点两次才生效，避免误触。
4. 分发前检查：`tools/precheck_release.py`（只读）会列出 `Data/`、`exports/`、`boot.log`、
   明文 Key、`.part` 残留，并给「能不能直接发」的结论，支持 `--json`。

**剩余**：DPAPI 只防「文件被拷走」，同一 Windows 用户下的任意进程仍可解密；真正更强的做法是
不保存 Key（每次启动输入）或走系统凭据管理器，按需再议。

## 5. 方案强依赖硬编码字段，抖音一改就瞎 · 优先级 P1（长期）

**现状**：以下全部是逆向出来的常量，没有任何远端探测或降级自检：
- IM 请求 envelope：外层 `301 / 10027 / '0.1.6' / 'fef1a80:p/lzg/store' / 'douyin_pc' / '360000'`；
- 消息字段表：`f3=server_id、f4=created_at_us、f7=sender_uid、f8=content_json、f10=real_ms、
  f11=is_recalled、f12=visible、f14=sender_sec_uid、f17=seq、f18=引用`；
- aweType 分类表：文本 `[0,700,701,703]`、表情 `[500,501,507,508,510,514,516]`、
  图片 `[2702,2703,2704]`、分享 `[11029,10500,10401]`；
- 媒体：图片 AES-256-GCM（skey 32B、密文前 12B 当 IV）、视频 MPEG-CENC（skey 16B、逐 sample CTR）。

**已经因此翻过车**：本轮实测发现 11054/11063 用的是蛇形 `item_id` + `description` + `aweme_info`，
而 `render()` 只认驼峰 `itemId` + `content_title`，导致 192 条分享卡片退化成原始长文本；
720/712（带 @提及的富文本，441 条）不在 TEXT_T 里也被归成 other。

**处理**：
1. 字段表外置成随包的 **`im-schema.json`**（`ep / msg / resp / req / awe / share` 六组），
   `app.py` 启动时注入为 `window.__DYIN_SCHEMA`，`injector.js` 保留同值内置默认兜底；
   exe 场景下**程序目录里放一份就优先读它**（`schema_path()`），所以改版真的不用重编译。
2. `buildRequest` 由字段表驱动，并用 `tools/check_render.js` 做了**逐字节比对**（新旧实现输出必须一致），
   `im-schema.json` 与内置默认还做键名/取值漂移检查，改错键会当场 FAIL 而不是静默失效。
3. `render()` 落到兜底时按 aweType 去重上报一次：
   `[schema-miss] aweType=11052 走文本兜底 keys=[aweType,cover_url,description]（要补就改 im-schema.json 的 awe 表）`，
   用户发来 boot.log 就能直接看到该补什么（harness 已验证确实会写出去）。
4. 首页 smoke test：某会话第一页就解析不出消息时，弹窗与提示改成
   「有 N 个会话首页就没解析到消息——接口字段可能已变更」，不再表现为「拉了 0 条」这种假象。

**剩余边界**：媒体加密参数（AES-GCM 的 12B IV、CENC 的 skey 16B）仍写在 `media.py` 里，没进 schema；
真要改到那一步说明抖音换了加密方案，得重新逆向而不只是改表。
`f11=is_recalled / f12=visible` 的语义仍是推断（见第 6 条），只做诊断不做显示判断。

## 6. `[未知]` 与拉取吞吐（附带发现）

- **本轮已修**：用 `tools/check_render.js` 对本机 6722 条真实消息回归，分类被纠正 789 条——
  720/712（@提及富文本，441 条）归回文本；`11052/11054/11063` 的新结构分享卡片
  （蛇形 `item_id` + `description`，192 条）不再退化成原始长文本；评论分享（10500）
  从「空标题视频卡」纠正为 `[分享] 分享评论 …`；打招呼卡片可读出正文。
  剩下的 34 条 `content_json` 本身为空/非 JSON，**属于接口就没给正文而非渲染不出**，
  现在文案改成「无内容 · 无法解析（可能已撤回或为该客户端专有卡片）」，不再显示 `[未知]`。
  已补：`is_recalled / visible` 现在随每条消息写进 JSON（`recalled` / `visible`），阅读器
  「会话详情」在统计到时会显示「撤回标记 N 条」。**只作诊断、不改显示文案**——
  f11 的语义仍是逆向推断，万一猜偏也不会把正常消息标成撤回。
  另按用户要求：无内容消息（`blank`）与打招呼卡片（`greeting`）**默认不在阅读器与
  HTML/TXT/CSV 里出现**，JSON 保留全量并带上这两个标记；HTML 头部、阅读器计数条与
  会话详情都会写明「另有 N 条未显示 / 已隐藏」，不会让人误以为聊天变少了。
  （`[未支持的消息类型 xxx]` 仍然显示，方便发现新类型。）
- **语音转文字 400（真机复现）**：`input_audio.format must be one of: wav, mp3. Got: m4a`——
  MiMo 这类网关的 chat 形态不收 m4a，而抖音语音 232 条全是 m4a。已加自动转码
  （`to_chat_audio`：系统 ffmpeg 优先，其次 `imageio-ffmpeg`，转 16k 单声道 mp3 再上传），
  用本机真实语音 + 真实网关验证通过（返回了正确文本）。两者都没有时给出可操作的中文提示，
  而不是把 400 原文丢给用户。`requirements.txt` 已把 `imageio-ffmpeg` 从"仅开发用"改成正式依赖。
- **每转一条语音闪一个 cmd 黑框**（用户实测反馈）：`to_chat_audio` 用 `subprocess` 起 ffmpeg，
  而宿主是 pythonw / `console=False`，spawn 控制台程序会各开一个新窗口，231 条就是 231 次。
  已给全部三处外部命令（语音转码 ffmpeg、`media._faststart` ffmpeg、TTS 测试 powershell）加
  `creationflags=CREATE_NO_WINDOW` + `stdin=DEVNULL`，并在 `test_export.py` 里断言参数确实传了
  （`NO_WINDOW=134217728`）。
- **导出阶段进度条一直停在 0%**：`pmBar` 以前只在拉取阶段和结束时被调用，导出全程不动。
  现在引入整体进度模型 `plan`：转写占 20%，其余 78% 按「格式数 × 会话数 × 会话内阶段
  （媒体 0.55 / 头像 0.8 / 写入 0.9→1.0）」折算，实测从 2% 单调推进到 100%。
- **长任务把人关在弹窗里**：曾加过「收起 → 右下角小条」的逃生口，但用户明确要求去掉
  （导出期间就该只能等），现已移除；同时保留随之发现的进度条起点问题修复：
  新任务开始时进度条从 0 重新计（关掉过渡再强制重排），不再出现"上一轮 100% 慢慢缩回来"、
  看起来一开始就快满了的现象。
- 多会话仍是**串行**拉取（几十个会话的大批量备份会比较久），2 路并发留作后续优化。
- `media._urllib_transport` 的 timeout 是单次 recv 静默上限（已注释说明为 20s），
  批量下载 1486 项媒体实测 2.5 秒（多数命中「已存在跳过」），首下慢属带宽瓶颈，非代码问题。

## 7. 本轮补修的其它两件事

- **语音转写失败没有任何原因记录**：`boot.log` 里只留下 `阅读器语音转文字: 成功0 失败2`
  （本机 21:18 真实跑过一次，两条全失败但查不到为什么）。现在 JS 侧记
  `语音转写失败 sid=… ：<接口返回片段>`，Python 侧记 `[转文字失败] 会话/sid @模型：<错误>`，
  齿轮里的「▶ 测试」仍可当场验证接口通不通。
- **测试脚手架自身的坑**：`tools/ui_harness.html` 第一版把桥 mock 写成返回普通对象，
  而真实 pywebview 一律返回 Promise，导致四条格式全部在 `begin_export(...).then` 处炸掉——
  这是 harness 的错，不是产品的错。现在 mock 统一包一层 `Promise.resolve`，
  并且 harness 会先读 `im-schema.json` 再加载 `injector.js`，时序与 `app.py` 一致。

## 8. 「文字已经全部转语音，怎么还有的没有加载出文字」（真机数据）

结论：**不是渲染问题，是那 81 条真的没转成功**。本机 `Sxxxx` 会话的实测：

- `media/voice/` 里 231 个 `.m4a`、只有 150 个 `.txt`；导出 JSON 里带 `asr` 的也是 150 条。
- `boot.log`：`23:04:11 [JS] 导出前语音转写: 成功150 失败81 共231` +
  `失败示例: HTTP 429`。整份日志里 `HTTP 429` 出现 173 次 —— 网关侧限流
  （请求过于频繁），不是文件损坏、也不是格式问题（400 那条早已通过转码解决）。

由此还暴露出两个连带缺陷，都已修：

- **重启后已转好的文字读不回来**：转写结果以前只活在页面内存 `state.asrText`，
  关掉软件就没了 —— 阅读器气泡是空的，而且**再导出一次会把 JSON 里已有的 `asr` 冲成 null**。
  现在 Python 侧加 `voice_texts(会话名)`（读 `media/voice/*.txt`），JS 侧 `hydrateAsr()`
  在「点导出前 / 自动快照前 / 打开阅读器内存视图」三处回填。
  harness 验证：刷新页面（等价于重启软件）后打开阅读器，2 条语音气泡都显示缓存文字，
  `transcribe_one` 调用次数 0；再关掉「语音转文字」导一次 JSON，`asr` 字段仍在（12 条消息、2 条带 asr）。
- **限流没有退避**：`_post_transcribe` 现在按状态码判定可重试（429/408/5xx/网络异常），
  最多 4 次；429 优先读 `Retry-After`，没有就 4s 起指数退避（上限 60s），其它 2s 起。
  400 这类参数错误不重试（重试也不会好）。转写并发 3 → **2**，减少触发限流的概率。

还没转的语音怎么补：进「聊天记录」→ 右上角语音转文字图标，弹窗**默认只勾选未转写的**，
点「开始转写」即可；已成功的 150 条直接命中 `.txt` 缓存，不会再花钱请求一次。
如果反复 429，就是网关配额本身，隔一会儿再补跑一轮即可（失败原因现在都会写进 `boot.log`）。

## 9. 标题栏配色与图标（用户追加）

- 标题栏是 DWM 画的，pywebview 没有配色接口 → 走 `DwmSetWindowAttribute`：
  35 底色、36 文字色、34 边框色（与底色同色，不留一条亮边）、20 深色模式（决定最小化/关闭键深浅）。
  颜色取自 `injector.js` 的 `--bg` / `--text`，所以浅色是 `#f5f6f8`、深色是 `#17181c`。
- **`icon` 是 `webview.start()` 的参数，不是 `create_window()` 的**：写进 `create_window` 直接
  `TypeError: create_window() got an unexpected keyword argument 'icon'`，软件根本起不来。
  这条是真机冒烟跑出来的（离线测试全都绿），已在 `main()` 里放对位置并写了注释。
- 图标必须两套：同一张图在深色标题栏上几乎看不见（`tools/_icon_pair.png` 对比过），
  所以 `app-icon.ico`（深描边）+ `app-icon-dark.ico`（浅描边），切主题时连同配色一起换。
  原生成图的「透明」是画上去的浅灰棋盘、右下角还带水印，`tools/make_icon.py` 负责处理。
- `DwmGetWindowAttribute` 读不回 34/35/36（实测返回失败），所以「有没有生效」只能看 HRESULT，
  或者截屏比像素 —— 后者在**屏幕锁定时会蒙出错**：截到的是锁屏桌布，深浅两次颜色一模一样，
  曾经就这样蒙通过一次「深色主题像素正确」。`tools/check_titlebar.py` 现在会先判断
  输入桌面是不是 `Default` 并比较两次取样，条件不满足就明确打印「跳过」而不是给结论。
- 主题选择存在 `Data/ui_theme.txt`：建窗口时就要决定图标和初始配色，等不到页面里的 localStorage。
  真机日志形如 `[标题栏] 启动按主题 light 设色：hr={'20':0,'35':0,'36':0,'34':0}`、
  `[标题栏] 主题切换 → light：… 图标=True`。
